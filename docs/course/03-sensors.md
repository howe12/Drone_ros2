# 03 传感器话题桥接

> 难度 L1 · 对应实验 E1 · 视觉/SLAM/避障三章的前置 · 预计 40 分钟

## 本章问题

前两章你只用了一架"裸机"：除了 IMU，它什么传感器都没有。

可到了第 5 章要做 YOLO 检测，第 7 章要用激光建图，第 9 章要拿深度图避障——**同一架飞机，怎么突然就有了相机和激光？**

答案是：换机型。但要解决三个问题：

1. 哪个任务该用哪个机型，怎么一条命令换装。
2. Gazebo 里的传感器数据，是怎么变成 ROS2 话题的。
3. 拿到的数据是不是真的——频率够不够、内参对不对、有没有脏数据。

第三点最容易被忽略，也最容易在后面的章节里埋雷。

## 学习目标

| 维度 | 学习前 | 学习后 |
|---|---|---|
| 机型选择 | 只会用默认的 `gz_x500` | 能按任务选机型，知道每种机型带什么传感器 |
| 桥接原理 | 以为话题是"自然就有"的 | 能画出 Gazebo 插件 → `ros_gz_bridge` → ROS2 话题这条链 |
| 数据验证 | 看到话题有数据就以为没问题 | 会用 `ros2 topic hz` 和 `camera_info` 核对频率与内参 |
| 数据质量 | 不知道点云里会有坏点 | 能识别并处理 `inf` 点和缺失字段 |
| 排障 | 节点收不到数据就怀疑代码 | 能区分"没发布"和"QoS 不匹配" |

## 前置知识

需要会用 `ros2 topic list`、`ros2 topic echo`（第 1 章用过）。不要求懂图像处理或点云算法。

**先跑，再懂。** 第 1 节先换一架带相机的飞机，看到图像；第 2 节解释数据是怎么流过来的。频率和内参这类数字，第一遍不用记，会用命令查就行。

## 1. 先让它动起来（最小路径）

### 1.1 换一架带相机的飞机

```bash
bash scripts/run_simulation.sh xtd2 gz_x500_mono_cam
```

注意命令末尾多了个参数——这就是"换机型"。命名空间会跟着变：

```text
gz_x500            → /x500_0
gz_x500_mono_cam   → /x500_mono_cam_0
```

规则是固定的：**机型名去掉 `gz_` 前缀，加 `_实例号`**。第 1 架实例号是 0。

### 1.2 看图像与频率

新终端：

```bash
source /opt/ros/humble/setup.bash
source <仓库路径>/ros2_ws/install/setup.bash

ros2 topic hz /x500_mono_cam_0/camera/image_raw
```

预期输出（约 3 秒后开始打印）：

```text
average rate: 23.6
	min: 0.035s max: 0.052s std dev: 0.003s window: 25
```

**23.6 Hz** —— 记住这个数，它决定了后面视觉算法的上限。相机只有 23.6 帧/秒时，你的检测不可能比它更快。

![相机画面](images/07_camera_frame.png)

**相机看到的画面：机头前方的世界，1280×960。**

### 1.3 确认内参

```bash
ros2 topic echo /x500_mono_cam_0/camera/camera_info --once | grep -A2 "k:"
```

预期能看到 `fx`、`fy` ≈ **539.94**，以及图像宽高 1280×960。**内参**是相机的"焦距与像素的换算比例"，测距、反投影、VIO 全靠它；内参错了，算出来的距离就全错。

## 2. 刚才发生了什么（回头理解原理）

### 2.1 为什么"换个任务"要换机型

传感器的**物理属性**，不是软件开关。多装一个相机，意味着模型上多一个挂载点、多一份质量、多一条数据线。所以课程把它们做成了不同机型：

| 机型 | 传感器 | 启动命令 | 后续用在哪 |
|---|---|---|---|
| `gz_x500` | IMU | `run_simulation.sh xtd2` | 控制入门 |
| `gz_x500_mono_cam` | 前置单目相机 | `run_simulation.sh xtd2 gz_x500_mono_cam` | 05 YOLO / 08 VIO |
| `gz_x500_depth` | OakD 深度相机 | `run_simulation.sh xtd2 gz_x500_depth` | 09 避障 |
| `gz_x500_mono_cam_down` | 下视相机（自建机架 4013） | `run_simulation.sh xtd2 gz_x500_mono_cam_down` | 06 精准降落 |
| `gz_x500_lidar_2d` | 2D 激光（自建机架 4012） | `run_simulation.sh xtd2 gz_x500_lidar_2d` | 07 2D SLAM |
| `gz_x500_lidar_3d` | 16 线 3D 激光（自建机架 4014） | `run_simulation.sh xtd2 gz_x500_lidar_3d` | 07 3D SLAM |

**机架（airframe）**是 PX4 的概念：一份"机型 + 参数"的配置模板，决定飞控用哪套控制器和混控。课程的 4012/4013/4014 是自建机架，用来让 PX4 认识这三种新机型。

### 2.2 数据是怎么流过来的

```text
Gazebo 传感器插件 --gz.transport--> ros_gz_bridge(parameter_bridge) --DDS--> ROS2 话题
```

三步：

1. **Gazebo 插件**在仿真里产生数据（相机渲染出图、激光算交点）；
2. **`ros_gz_bridge`** 把 gz.transport 的消息转成 ROS2 消息类型；
3. 转换后的消息发到 DDS，于是 `ros2 topic echo` 能看到。

桥接配置是 YAML 模板，按命名空间实例化；课程补丁 0007/0008 加了三个自建机架和传感器桥接扩展，补丁 0011 加了 `/clock` 与带协方差的里程计（SLAM 需要）。

> **Humble 的 `ros_gz` 必须源码编译才能对接 Harmonic**——官方二进制只支持 Fortress。这一步 `setup_workspace.sh` 已经处理，你不需要手做。

### 2.3 各类传感器的实测频率

下表是本仓库实测值（`{ns}` 替换成实际命名空间）：

| 话题 | 类型 | 实测 |
|---|---|---|
| `{ns}/camera/image_raw` | sensor_msgs/Image | 23.6 Hz, 1280×960 |
| `{ns}/camera/camera_info` | CameraInfo | 内参 fx=fy=539.94 |
| `{ns}/imu` | sensor_msgs/Imu | 253 Hz（含重力） |
| `{ns}/scan` | sensor_msgs/LaserScan | 30.4 Hz, 270°/30m |
| `{ns}/depth_camera/image_raw` | Image（深度） | 25.6 Hz |
| `{ns}/depth_camera/points` | PointCloud2 | 28.1 Hz |
| `{ns}/lidar_3d/points` | PointCloud2（16 线） | 见第 7 章 |
| `{ns}/pose` | PoseArray | **gz 世界系真值**（判分用） |
| `/clock` | Clock | 仿真时钟（`use_sim_time` 全链路） |

几个名词：

- **IMU**：惯性测量单元，输出加速度和角速度，253 Hz。它是飞控和 VIO 的核心输入。
- **LaserScan**：2D 激光的一圈距离读数；**PointCloud2** 是三维点云。两者都是"点"，但 2D 是一圈、3D 是一片。
- **`/clock` 与 `use_sim_time`**：仿真里时间要跟着仿真走而不是墙上时钟，否则 TF 和消息时间戳会打架。节点必须设 `use_sim_time:=true`。

### 2.4 频率差意味着什么

IMU 253 Hz，相机 23.6 Hz，相差十倍。

这不是设计缺陷，而是物理现实：IMU 是电子器件，读得快；相机要曝光和传输，慢得多。**快的准不了（IMU 积分会漂），准的快不了（相机帧率低）**——所以要融合。这正是第 8 章 VIO（视觉惯性里程计）要解决的问题：用 253 Hz 的 IMU 补 23.6 Hz 相机的空档。

### 2.5 相机内参：那三个数字是怎么来的

`camera_info` 里的 `k` 数组：

```text
k = [fx,  0, cx,
      0, fy, cy,
      0,  0,  1]
```

| 符号 | 含义 | 本仿真值 |
|---|---|---|
| `fx` | x 方向焦距（像素） | 539.94 |
| `fy` | y 方向焦距（像素） | 539.94 |
| `cx` | 光心在图像上的 x 坐标（像素） | ≈ 640 |
| `cy` | 光心在图像上的 y 坐标（像素） | ≈ 480 |

**为什么焦距用"像素"表示**：物理焦距是毫米，但计算时我们要的是"像素偏移 → 角度"的换算系数。把物理焦距除以像元尺寸，就得到像素焦距。

**针孔模型的最小用法**：一个物体在图像上偏离光心 `Δpx` 像素，它的视线方向偏离光轴的角度约为：

```text
θ ≈ atan(Δpx / f)
```

例如 `Δpx = 200`、`f = 540`：`θ ≈ atan(0.37) ≈ 20°`。

**cx/cy 为什么可能不是正好一半**：装配误差会让光心略微偏移。本仿真是理想值（正好 640/480），实机需要标定（第 15 章）。

> **内参错了会怎样**：所有基于图像的测距、反投影、视觉伺服都会系统性偏。第 6 章精准降落的落点偏差，一部分就来自内参误差。

### 2.6 激光扫描：一圈距离怎么读

`sensor_msgs/LaserScan` 的核心字段：

| 字段 | 含义 | 本仿真值 |
|---|---|---|
| `ranges` | 每个角度的距离数组（米） | 长度约 540 |
| `angle_min` / `angle_max` | 扫描起止角 | -135° / +135° |
| `angle_increment` | 相邻两束的角度差 | 约 0.5° |
| `range_min` / `range_max` | 有效量程 | 0.1 / 30 m |

**270° 视场、30m 量程**意味着：它只能看到前方和两侧，看不到正后方；超出 30m 或没有回波的点会填 `inf`。

**读法**：`ranges[i]` 对应角度 `angle_min + i × angle_increment`。要判断"正前方有没有障碍"，就取角度接近 0 的那几束，看最小值。

**为什么雷达是"一圈"而相机是"一片"**：激光是单束扫描（或少数线），相机是整幅成像。所以 2D 激光建图只得到一个平面切片（第 7 章）。

### 2.7 点云：三维点是怎么组织的

`sensor_msgs/PointCloud2` 是**二进制点数组**，字段由 `fields` 描述：

| 字段 | 类型 | 含义 |
|---|---|---|
| `x` / `y` / `z` | float32 | 点的三维坐标 |
| `intensity` | float32 | 反射强度（模拟量） |
| `ring` | uint16 | 线号（16 线激光时 0–15） |
| `time` | float32 | 点内时间偏移（0–扫描周期） |

课程里两个点云来源的差异：

| 来源 | 有 `ring`/`time` 吗 | 后果 |
|---|---|---|
| Gazebo 原生点云 | ❌ 只有 xyz+intensity | 3D LIO 拒收（第 7 章） |
| 课程适配器输出 | ✅ 补齐 | 可进 Point-LIO |

**`width` / `height` 的含义**：`height=1` 叫"无序点云"（一维数组）；`height>1` 叫"有序点云"（像图像一样按行列组织）。Gazebo 的点云通常是无序的。

### 2.8 时间：为什么所有节点都要 `use_sim_time`

仿真里的时间有三个来源：

| 来源 | 含义 |
|---|---|
| 墙上时钟 | 真实世界时间 |
| `/clock` | Gazebo 仿真时间 |
| 消息 `header.stamp` | 数据产生的时刻（仿真时间） |

**如果节点用墙上时钟**：它算出的"消息年龄"会是几十年（因为仿真时间从 0 开始），TF 会拒绝"来自太久以前"的变换，表现为**节点在跑、TF 在发、就是没结果**（第 7 章的静默失败就是这么来的）。

**正确做法**：所有节点都设 `use_sim_time:=true`，让它们统一读 `/clock`。

```bash
ros2 param get /slam_toolbox use_sim_time     # 应为 True
ros2 topic hz /clock                          # 应有数据
```

## 3. 扩展：案例与排障

### 案例 1：`ros2 topic echo` 能收到，节点收不到

**现象**：手动 `ros2 topic echo` 有数据，但自己写的订阅节点一条也收不到，也不报错。

**原因**：QoS 不匹配。传感器话题发布端是 **BEST_EFFORT**，订阅端若用默认 **RELIABLE**，两者不兼容——**静默收不到，不报错**。

**修复**：订阅时显式指定：

```python
from rclpy.qos import QoSProfile, ReliabilityPolicy
qos = QoSProfile(depth=10, reliability=ReliabilityPolicy.BEST_EFFORT)
self.create_subscription(Image, topic, self.cb, qos)
```

**要点**：这是本课程最隐蔽的一类故障——**没有错误信息**。凡是"话题有数据、节点收不到"，先查 QoS。

### 案例 2：点云里的 `inf` 点

**现象**：激光打到远处没有回波，点云里出现 `inf` 坐标。

**后果**：直接喂给 LIO（激光惯性里程计）会破坏内部数据结构（ikd-tree），导致位姿发散、建图崩掉。

**修复**：过滤。第 7 章的 `lidar3d_adapter.py` 做这件事——进算法前先剔除 `inf`/`nan` 点。

### 案例 3：点云缺 `ring` / `time` 字段

**现象**：Gazebo 产出的点云没有"线号"（`ring`）和"每点时间戳"（`time`）。

**后果**：3D LIO 需要按线号和点内时间做运动补偿，缺这两个字段会直接报错或用错数据。

**修复**：`lidar3d_adapter.py` 按线序补齐这两个字段。这是"仿真器给的"和"算法要的"不一致的典型例子。

### 案例 4：明明有图，检测却很慢

**现象**：图像话题正常 20+ Hz，但下游节点处理不过来，队列越积越多，延迟越来越大。

**原因**：订阅端处理速度 < 发布速度。ROS2 的队列（`depth`）满了会**丢最旧的**，于是你看到的永远是"过期图像"。

**诊断**：

```bash
ros2 topic hz <输出话题>          # 输出频率是否远低于输入
ros2 topic delay <输入话题>       # 消息年龄是否在增长
```

**处理**：

| 手段 | 作用 |
|---|---|
| 降低订阅 `depth` | 只保留最新帧，不积压 |
| 提高处理速度（降分辨率/降频） | 从源头解决 |
| 显式丢帧（每 N 帧处理一次） | 第 5 章的 `infer_every_n` |

**教训**：**"话题有数据"不等于"数据是新的"**。实时系统关心的是**延迟**，不是吞吐。

### 案例 5：换机型后话题名对不上

**现象**：换了 `gz_x500_depth`，但脚本里写的还是 `/x500_mono_cam_0/camera/image_raw`，收不到数据。

**原因**：命名空间随机型变化（第 1 章的推导规则）。

**验证**：

```bash
ros2 topic list | grep -E "camera|depth|scan" | sort
```

**处理**：把命名空间做成参数，而不是写死在脚本里（这也是课程所有节点都声明 `camera_ns` / `px4_ns` 参数的原因）。

## 常见误解

| 误解 | 实际情况 |
|---|---|
| "话题有数据就说明链路正常" | 还要看频率、延迟、QoS、内容是否合理 |
| "图像就是一张图片" | 是裸像素缓冲 + 编码 + step |
| "内参是相机出厂就对的" | 实机必须标定，仿真才是理想值 |
| "激光能看见四周" | 270° 视场，有盲区（正后方看不到） |
| "点云越密越好" | 含 `inf`/离群点会毁掉算法 |
| "频率越高越好" | 关键看端到端延迟与数据新鲜度 |
| "用默认 QoS 就行" | 传感器话题必须 BEST_EFFORT（第 2 章） |
| "仿真时间没必要管" | 不设 `use_sim_time` 会导致 TF 静默失效 |

## 4. 进阶：从"有数据"到"用得好"

### 4.1 带宽估算

多传感器同时开，带宽会迅速上去。粗算：

```text
图像：1280 × 960 × 3 字节 ≈ 3.7 MB/帧 × 20 Hz ≈ 74 MB/s
点云：每点 24 字节 × 4.4 万点 × 8 Hz ≈ 8.4 MB/s
```

**这就是为什么实机不能把所有原始数据都传回地面站**（第 15 章）。仿真里是内存/本地网络，看不出来；实机上会立刻卡死。

**对策**：机上处理、只传结果（检测框、位姿），或用压缩（`image_transport` 的 compressed 插件）。

### 4.2 传感器选择：什么任务用什么传感器

| 任务 | 首选传感器 | 理由 |
|---|---|---|
| 目标检测 | 单目相机 | 只要图像 |
| 精准降落 | 下视相机 + ArUco | 需要近距离、高分辨率 |
| 室内定位 | 激光 或 相机+IMU | 无 GPS |
| 避障 | 深度相机 / 3D 激光 | 需要距离与点云 |
| 室外长航时 | GPS + 气压计 | 不需要密集感知 |

**没有"最好的传感器"，只有"匹配任务的传感器"**——这也是第 4 章"场景—机型—指标"契约的另一面。

## 分层练习

**基础**

1. `fx = 540`、物体偏离光心 270 像素，算出视线偏角。
   > 要点：`atan(270/540) = atan(0.5) ≈ 26.6°`。

2. 激光 `angle_min=-135°`、`angle_increment=0.5°`，第 270 个点对应哪个角度？
   > 要点：`-135 + 270×0.5 = 0°`（正前方）。

3. `height=1` 的点云叫什么？为什么不影响使用？
   > 要点：无序点云；三维坐标自带，只是没有行列结构。

**进阶**

4. 用 `camera_info` 的 `k` 反推"图像四个角对应的视场角"，并与"标称 FOV"对比。

5. 把深度图的 `0.1 < d < 20` 过滤条件改成 `0.5 < d < 10`，观察第 9 章避障行为变化。

6. 写一个脚本，同时打印三路传感器的 `header.stamp` 与 `/clock`，判断谁的时间戳不新鲜。

**挑战**

7. 设计一个"传感器健康检查"节点：频率低于阈值、或时间戳落后超过 0.5s 就报警。

8. 估算：如果要把 1280×960 图像以 20Hz 传到另一台机器，需要多大带宽？给出压缩方案。

# 16 自动判分与作业系统

> 平台 L2 层 · 本课程"可执行判定"的核心 · 面向学生与课程作者 · 预计 90–120 分钟

## 本章问题

前十五章，每一章结尾都有"判分"。你可能已经习惯了：跑一条命令，看几个 PASS。

但你有没有想过：

- 为什么**单次成功不算通过**？
- 为什么位置类指标一定要用 Gazebo 的世界系真值，而不能用飞机自己报的位置？
- 为什么每个指标都必须写清"**怎么取数**"？
- 如果我是出题人，怎么设计一套**不能被糊弄**的判分？

这一章换视角：**你从"学习者"变成"出题人"**。

要解决四件事：

1. 判分系统怎么用（学生视角）。
2. 三条判分铁律，各自对应哪种血泪教训。
3. 场景目录契约：怎么新增一个可判分的实验。
4. 判分系统**自身的局限**——为什么它也可能被骗。

第 4 点是本章最有价值的：**任何自动判分都可能被刷分**，第 13 章那个"飞走的飞机让间距指标变好看"就是活例子。

## 学习目标

| 维度 | 学习前 | 学习后 |
|---|---|---|
| 判分使用 | 只会跑一条命令看 PASS | 会用 `--runs`、`--json`、`--md` 出正式报告 |
| 指标设计 | 以为"跑通"就是通过 | 理解指标必须可量化、可复现、有取法 |
| 统计口径 | 单次成功就满意 | 知道要 N 次通过率，理解为什么 |
| 真值选择 | 用飞机报的位置判断 | 知道位置类指标必须用外部真值 |
| 契约意识 | 命令靠自己记 | 知道 `scenarios.yaml` 是唯一事实源 |
| 批判思维 | 判分 PASS 就放心 | 能指出判分可能的刷分漏洞 |

## 1. 学生用法：三种模式

### 1.1 看有哪些场景

```bash
python3 tools/grade.py --list
```

输出的是场景 id 列表，比如 `ctrl.takeoff_hover_land`、`ctrl.waypoint_square`、`vision.yolo_detect`……

**场景 id 是课程的"实验编号"**：每章的判分命令都用它，你不用记命令细节。

### 1.2 快速自测（`--runs 1`）

```bash
python3 tools/grade.py --scenario ctrl.takeoff_hover_land --runs 1
```

跑一次，看指标。**适合开发阶段快速验证**，但不适合作为最终结论（见 2.2）。

### 1.3 正式判分（`--runs 3` + 报告）

```bash
python3 tools/grade.py --scenario ctrl.waypoint_square --runs 3 \
    --json out.json --md out.md
```

产出两个文件：

| 文件 | 用途 |
|---|---|
| `out.json` | 机器可读（每次运行的指标、PASS/FAIL、汇总） |
| `out.md` | 人可读（表格形式，可直接贴进实验报告） |

**作业交的是这两个文件，不是"我觉得飞得挺好"。**

### 1.4 判分做了什么

`grade.py` 自动完成一条链路：

```text
起仿真栈 → 跑场景命令 → 采样 ROS 话题 → 对照阈值 → 出报告
```

它有三个工程细节值得学：

| 细节 | 做法 | 解决什么 |
|---|---|---|
| 进程管理 | `start_new_session=True`，按**进程组**终止 | 避免 `pkill` 模式匹配误杀自己（本仓库踩过） |
| 就绪等待 | 等 PX4 与状态话题，不靠 `sleep` | 避免"启得慢就判失败" |
| 清理残留 | 启动前清场 | 避免上一轮的仿真干扰本轮 |

> **`pkill` 自伤**这条：本仓库开发时多次出现"`pkill -f xxx` 把自己的 shell 也杀了"。改用进程组是根本解法——这也是为什么代码里专门写了 `start_new_session=True`。

> 需要 GUI 的场景要在能访问 X 的终端跑（`DISPLAY=:0`）。

## 2. 三条铁律：每一条都是一次教训

### 2.1 铁律一：指标化

**规则**：每个场景必须有 `metrics`，每项含 `name / threshold / unit / how`。

**为什么**：不接受"看起来正常"。

**反例**（课程早期真实存在过）："飞机平稳起飞并降落" —— 这不是指标，是描述。不同人对"平稳"的标准不同，也无法复现。

**正例**：

```yaml
metrics:
  - {name: 起飞高度误差, threshold: '< 0.4', unit: m,
     how: '起飞后高度与目标高度之差的中位数'}
```

**关键在 `how`**：它说清"怎么取数"。没有 `how`，同一个指标两个人能算出两个值。

### 2.2 铁律二：N 次通过率

**规则**：默认 N=3，要求 **≥2/3** 通过。单次成功不算 PASS。

**为什么**：单次成功可能是运气。

**本仓库的真实教训**：

| 实验 | 现象 |
|---|---|
| E7 避障 | 第 7 次才成功 |
| E10 行为树故障注入 | 从未成功（至今 open） |
| E9 集群 | 复测 0/3 到达 |

如果按"最好的一次"判定，这三个实验都会显示"通过"——**那就是自欺**。

**2/3 的含义**：允许一次偶然失败（仿真有随机性），但不允许"偶尔成功"。

### 2.3 铁律三：外部真值优先

**规则**：位置/精度类指标一律用 **Gazebo 世界系位姿**（`/<ns>/pose`）。

**为什么**：PX4 局部位置会重置原点。

**实测证据**：本仓库记录到 `xy_reset_counter=3`——一次飞行中局部原点被重置了 3 次。每次重置，局部坐标都会"瞬移"。

**如果你用局部坐标判精度**：

- 飞机会"自信地"报告自己在原点附近；
- 而 Gazebo 里它已经偏了 1 米。

第 6 章精准降落那个案例（"局部坐标说准了，真值说偏了 1 米"）就是这个铁律的来源。

### 2.4 三条铁律的关系

```text
指标化      → 让"成功"有定义
N 次通过率  → 让"成功"可复现
外部真值    → 让"成功"不撒谎
```

三缺一：

| 缺哪条 | 后果 |
|---|---|
| 缺指标化 | 无法判定，只能说"看着行" |
| 缺通过率 | 偶发成功被当成能力 |
| 缺真值 | 被系统自身的误差骗 |

## 3. 课程作者：场景目录契约

### 3.1 `scenarios.yaml` 是唯一事实源

**约定：不要自己编命令**。课程里所有命令都从 `catalog/scenarios.yaml` 来。

```yaml
- id: ctrl.waypoint_square        # 课程引用键
  level: L1                       # L0–L6 阶梯排课
  model: gz_x500                  # 传给 run_simulation.sh
  world: aruco
  command: |                      # 可复制的完整命令
    ros2 launch drone_sim waypoint_mission.launch.py prefix:=/x500_0 mission:=square
  metrics:                        # 判定标准
    - {name: 到点误差, threshold: '< 0.5', unit: m,
       how: '各航点最小接近距离的最大值'}
  pitfalls: [EKF原点重置导致贴地爬行]   # 故障实验室素材
  status: verified                # verified/partial/unverified/broken
```

**每个字段的作用**：

| 字段 | 谁用 | 作用 |
|---|---|---|
| `id` | 章节、判分命令 | 唯一引用键 |
| `level` | 排课 | L0–L6 难度阶梯 |
| `model` / `world` | 启动脚本 | 复现环境 |
| `command` | 学生、判分 | 可直接复制 |
| `metrics` | 判分 | 判定标准 |
| `pitfalls` | 故障实验室 | 真实踩过的坑 |
| `status` | 所有人 | **诚实标注** |

### 3.2 `status` 的四个取值

| 值 | 含义 | 能否当作业 |
|---|---|---|
| `verified` | 实测通过 | ✅ |
| `partial` | 部分通过 | ⚠️ 需说明 |
| `unverified` | 未验证 | ❌ **只能作研究挑战** |
| `broken` | 已知不可用 | ❌ |

**当前 `unverified` 的场景只有 `vio.vins_mono`**（第 8 章）——它被明确禁止作为作业。

**这条约定的价值**：它让"我们也有没做到的地方"变成**制度**，而不是靠自觉。

### 3.3 参数调参素材

`catalog/params.yaml` 收录了 14 个节点、84 个参数的注册表，由 `tools/gen_params.py` **自动生成**。

**不要手改**——它是从源码 `declare_parameter` 抽出来的。手改会在下次生成时被覆盖，还会导致文档与代码不一致（第 14 章就发现过两处漂移）。

## 4. 新增一个实验的三步

### 4.1 三步流程

| 步 | 做什么 | 检查点 |
|---|---|---|
| 1 | 节点用 `PX4Interface`，`declare_parameter` 暴露旋钮 | 不自己建 publisher（第 2 章） |
| 2 | `setup.py` 注册 console_scripts → `gen_params.py` | 参数注册表同步 |
| 3 | `scenarios.yaml` 加条目（含 metrics 与 pitfalls） | 跑 3 次验证 → 写章节 |

### 4.2 写 metrics 的要点

**坏的 metric**：

```yaml
- {name: 飞行成功, threshold: 'true', unit: '', how: '看日志'}
```

问题：`how` 不可执行，`threshold` 无意义。

**好的 metric**：

```yaml
- {name: 落点偏差, threshold: '< 0.15', unit: m,
   how: '结束时水平位置与靶标（世界原点）的距离，取 3 次中位数'}
```

三个要素齐：**可测量**、**有阈值**、**有取数方法**。

### 4.3 别忘了 `pitfalls`

`pitfalls` 不是装饰，它是**故障实验室的素材来源**。每一条应该是你真踩过的坑，比如"EKF 原点重置导致贴地爬行"。

**写 pitfalls 的好处**：学生遇到同样问题时，FAQ 里有据可查。

## 5. 判分系统自身的局限

这一节是本章的核心。

### 5.1 判分能防住什么

| 风险 | 判分能否防住 |
|---|---|
| 学生凭空写结论 | ✅ 必须跑出数据 |
| 单次运气好 | ✅ N 次通过率 |
| 用局部坐标美化精度 | ✅ 强制外部真值 |
| AI 代写作业 | ⚠️ 部分——判分不认文字，只认数据 |

**AI 代写这条**：判分系统让"AI 直接交答案"失效，因为必须真跑出 PASS。但 AI 可以帮学生调参、改代码——那是允许的（见 AI 指南的红绿灯）。

### 5.2 判分防不住什么

**核心弱点：指标可以被异常行为刷好看。**

第 13 章的活例子：

| 指标 | 结果 | 表面结论 |
|---|---|---|
| 最小间距 > 1.0m | 1.35m | PASS（"避碰成功"） |
| 全部到达 ≥ 3 | 2/3 | FAIL |

一架飞机**飞走了 52 米**——它离其他机越远，"最小间距"就越好看。

**如果只看第一个指标，会得出完全相反的结论。**

### 5.3 怎么设计"抗刷分"的指标

| 手段 | 例子 | 防什么 |
|---|---|---|
| **成对约束** | 完成数 + 安全间距 + 效率 | 单项被刷 |
| **上界型指标** | 路径长度 < 1.5×直线距离 | 飞远刷间距 |
| **时间上限** | 完成时间 < 90s | 磨蹭凑指标 |
| **趋势检查** | `goal_dist` 必须单调下降 | 越飞越远 |
| **人工抽查** | 看轨迹图 | 机器判不出的怪异行为 |

**通用原则**：

> 任何"越大越好"或"越小越好"的指标，都必须配一个**约束它别走极端**的指标。

否则系统会学会"刷那个指标"，而不是"完成任务"——这不是无人机的特例，是所有评估体系的通病。

### 5.4 判分的诚实边界

判分系统自己也该被诚实标注：

| 局限 | 表现 |
|---|---|
| 只能判"可测量的量" | 判不了"设计是否优雅" |
| 依赖仿真真值 | 实机上没有"上帝视角" |
| 指标可能被刷 | 需要成对设计与人工抽查 |
| 部分场景未验证 | `status: unverified` 不得当作业 |

## 6. 指标是怎么算出来的：读三个探针

前面说"每个指标都要有 `how`"，但 `how` 最终要落到代码。这一节看真代码。

### 6.1 探针机制

`grade.py` 里每个场景对应一个**探针函数**，用装饰器注册：

```python
@probe('ctrl.takeoff_hover_land')
def probe_takeoff(ctx, target_alt=5.0):
    ps = ctx.poses()
    max_alt = max((z for (_, _, _, z) in ps), default=0.0)
    ...
```

**设计要点**：探针只负责"采样 + 算数"，**不负责判定**。判定由场景 yaml 的 `threshold` 完成。

| 层 | 负责什么 | 在哪 |
|---|---|---|
| 采样 | 订阅话题、存时间序列 | `grade.py` 的 collector |
| 探针 | 从序列算出指标值 | `@probe` 函数 |
| 判定 | 值与阈值比较 | `scenarios.yaml` 的 `metrics` |

**为什么这样分层**：改阈值不用动代码，改算法不用动配置。**这也是"指标化"能落地的工程前提。**

### 6.2 采样时的关键一行：只取 t_start 之后

```python
def poses(self, ns=None):
    ns = ns or next(iter(self.s.poses))
    return [p for p in self.s.poses[ns] if p[0] >= self.t_start]
```

`t_start` 是**场景命令启动的时刻**。只取之后的数据，是因为前面可能有上一轮的残留。

**如果没有这个过滤会怎样**：上一轮的"最大高度"会被算进本轮，导致指标虚高或虚低——典型的**残留数据污染**。

> 这条与第 13 章的"指标污染"是一体两面：一个是"异常行为刷分"，一个是"脏数据刷分"。

### 6.3 探针一：`takeoff_hover_land`

```python
ps = ctx.poses()
max_alt = max((z for (_, _, _, z) in ps), default=0.0)
arms = ctx.arms()
t_arm = next((t for (t, a) in arms if a == 2), None)
t_disarm = next((t for (t, a) in arms if a == 1 and t_arm and t > t_arm), None)
```

**三件事**：

1. `max_alt`：整段飞行的最大高度（取 `z` 的最大值）；
2. `t_arm`：第一次出现 `arming_state == 2`（已解锁）的时刻；
3. `t_disarm`：解锁之后第一次出现 `== 1`（上锁）的时刻。

**注意 `t_disarm` 的条件里有 `t_arm and t > t_arm`**：必须先解锁再上锁，顺序不能反。否则会把"启动时的初始上锁状态"误当成"降落完成"。

**这就是 `how` 的具体含义**：不是"最后是否上锁"，而是"**解锁之后**是否上锁"。

### 6.4 探针二：`waypoint_square`

```python
wps = load_mission_waypoints(mission)
errs, hits = [], 0
```

它**从任务文件里读出航点坐标**，然后对每个航点算"轨迹到该点的最小距离"：

| 指标 | 算法 |
|---|---|
| 到点误差 | 各航点最小接近距离的**最大值** |
| 命中航点数 | 距离小于容差的航点数 |

**为什么"最大值"而不是"平均值"**：一个航点没飞到，平均值可能被其它三个拉低而"看起来还行"。**取最大值才能暴露最差的那个。**

这是"指标怎么选统计量"的又一个例子——和第 6 章的"中位偏差"、第 13 章的"间距"都是同一个主题。

### 6.5 探针的防御性写法

注意这一行：

```python
if not ps:
    return {'到点误差': 99.0, '命中航点数': 0, '结束状态': 0}
```

**没有数据时返回 99.0**，而不是抛异常或返回 0。

**为什么**：

| 做法 | 后果 |
|---|---|
| 抛异常 | 整个判分崩掉，其它场景也跑不了 |
| 返回 0 | 会被当成"误差为 0"，**假通过** |
| 返回 99.0 | 必然 FAIL，且原因明确 |

**"失败要显式失败"**——这是判分系统自身的安全设计。宁可报一个夸张的坏值，也不能让"没数据"变成"通过"。

## 常见误解

| 误解 | 实际情况 |
|---|---|
| "跑通一次就是通过" | 要求 N 次通过率（≥2/3） |
| "飞机说自己准就是准" | 必须用外部真值 |
| "指标越多越好" | 指标要有取法、成对约束，否则互相刷 |
| "判分 PASS 就没问题" | 可能被异常行为刷分（第 13 章） |
| "命令可以自己记" | `scenarios.yaml` 是唯一事实源 |
| "unverified 也能当作业" | 契约明确禁止 |
| "AI 能替学生过判分" | 判分只认数据，但 AI 能帮调参（允许） |

## 你可能卡在这里

| 现象 | 最可能原因 | 先跑这条命令 |
|---|---|---|
| `--list` 没有某场景 | 场景没登记 | 查 `catalog/scenarios.yaml` |
| 判分卡在"等待 PX4" | 环境/端口占用 | `ps -ef \| grep px4` |
| 判分结果每次差异大 | 仿真随机性 / 未通过率判定 | 用 `--runs 3` |
| 报告里指标为空 | 采样话题没数据 | 看场景 `how` 要求的话题 |
| 判分失败但人工看正常 | 指标口径与直觉不同 | 读 `metrics.how` |
| 想加场景但命令不对 | 自己编了命令 | 从已有条目的 `command` 抄结构 |
| 参数表和代码不一致 | 手改了 `params.yaml` | 重跑 `gen_params.py` |

### 任务卡 1：出一次正式判分报告

## 小结与下一步

本章你从"被评判"变成了"设计评判"。

三样东西值得带走：

1. **三条铁律**：指标化、N 次通过率、外部真值优先——它们是"可执行判定"的地基；
2. **场景契约**：`scenarios.yaml` 是唯一事实源，`status` 让不成熟的东西有地方待着；
3. **批判视角**：判分本身也可能被骗，必须用成对指标与人工抽查兜底。

最后一条尤其重要。第 13 章那次"飞走让指标变好看"，不是代码 bug，而是**评估设计的漏洞**。你在真实项目里做评测、写论文、看别人的 benchmark，都会遇到同类问题。

课程到这里结束。如果你是从第 00 章一路读下来的，现在应该能做到：

- 独立复现整套环境并跑通控制、感知、规划、多机的实验；
- 用判分系统证明结果，而不是"看起来还行"；
- 遇到跑不通的东西，能系统性地归因（第 8 章的方法论）；
- 并且知道**哪些结论只在仿真成立**（第 15 章）。

剩下的路在你自己手上：改一个参数、加一个场景、修一个已知缺陷（第 10、11、13、14 章各留了一个）。

## 附录：判分速查

### 命令

| 用途 | 命令 |
|---|---|
| 列出场景 | `python3 tools/grade.py --list` |
| 快速自测 | `python3 tools/grade.py --scenario <id> --runs 1` |
| 正式判分 | `python3 tools/grade.py --scenario <id> --runs 3 --json out.json --md out.md` |

### 场景字段

| 字段 | 必填 | 说明 |
|---|---|---|
| `id` | ✅ | 唯一引用键 |
| `level` | ✅ | L0–L6 |
| `model` / `world` | ✅ | 环境 |
| `command` | ✅ | 完整可复制命令 |
| `metrics` | ✅ | name / threshold / unit / how |
| `pitfalls` | 建议 | 故障实验室素材 |
| `status` | ✅ | verified / partial / unverified / broken |

### 三条铁律

| 铁律 | 防什么 |
|---|---|
| 指标化 | "看起来正常" |
| N 次通过率（≥2/3） | 偶发成功冒充能力 |
| 外部真值优先 | 系统自身误差骗人 |

### 判分已知局限

| 局限 | 对策 |
|---|---|
| 指标可被刷分 | 成对指标 + 上界约束 + 人工抽查 |
| 只能判可测量的量 | 主观质量靠人工评审 |
| 依赖仿真真值 | 实机需另设验证方式 |
| 部分场景未验证 | `status: unverified` 明确禁止当作业 |

# 11 安全监督与地理围栏

> 难度 L5 · 对应实验 E12（安全部分）· 场景 `safety.geofence` · 预计 120 分钟

## 本章问题

前面的章节都在教飞机"怎么把事做成"。这一章反过来：**怎么在它做错的时候把损失控制住**。

具体点说，下面这些情况必须有人管：

- 任务代码写错，飞机一直朝一个方向飞，越飞越远；
- 航点算错了，飞机要飞出场地边界；
- 姿态突然失控，翻着跟头往下掉；
- 你在现场发现不对，想立刻让它停下来。

**关键问题是：这些检查不能写进任务代码里**。因为任务代码本身可能就是出问题的那一方——它崩了、卡死了、算错了，就没人检查了。

所以要有一个**独立于任务的监督者**：它不参与任务，只盯着状态，一旦越界就接管。

这一章要解决四件事：

1. 为什么安全层必须独立。
2. 五类检查各自该触发什么动作（RTL 还是 LAND，为什么）。
3. 为什么"近似算法"在安全层里是致命的（我们踩过）。
4. 监督层自己失效了怎么办。

## 学习目标

| 维度 | 学习前 | 学习后 |
|---|---|---|
| 安全架构 | 把检查写进任务里 | 理解监督层必须独立、只订阅只发命令 |
| 动作选择 | 出问题就降落 | 知道 RTL 与 LAND 的适用场景差异 |
| 姿态计算 | 用速度比近似倾角 | 会用四元数算真实倾角，知道近似何时撒谎 |
| 阈值设计 | 凭感觉设数字 | 会按任务包络推导阈值 |
| 失效分析 | 假设监督层不会挂 | 能说出监督层自身的失效模式 |
| 排障 | 误报就关掉检查 | 能区分"阈值不对"与"量算错了" |

## 前置知识

需要会第 2 章的状态查询（`vehicle_status`、`vehicle_local_position`）、第 4 章的航点任务。倾角部分会用到四元数，本章会解释用到的那个分量含义。

**先跑，再懂。** 第 1 节先让它"越界被抓"，看到 RTL 日志；第 2 节再讲设计。

## 2. 刚才发生了什么（回头理解原理）

### 2.1 为什么监督层必须独立

设想把检查写进任务代码：

```python
# 反例：安全检查写在任务里
if dist > max_radius:
    rtl()
goto(next_waypoint)
```

问题有三层：

| 问题 | 说明 |
|---|---|
| **任务挂了就不检查** | 任务代码崩溃/卡死，检查也一起没了 |
| **检查会被"绕过"** | 新写的任务节点忘了加这段 |
| **职责混淆** | 任务逻辑与安全逻辑纠缠，改一处影响另一处 |

**独立监督层**的约定很硬：

| 约束 | 含义 |
|---|---|
| **只订阅状态** | 不控制任务，不改目标 |
| **只发安全命令** | RTL / LAND / 速度限制 |
| **不依赖任务节点存活** | 任务崩了它照样工作 |
| **自身尽量简单** | 代码越少越不容易错 |

这是实机部署的标准范式——第 15 章 Sim2Real 会再见到同样的结构。

### 2.2 五类检查与动作选择

代码里的检查顺序（`loop()` 里从上到下）：

```python
if self.estop:                    # ① 外部急停 → LAND
if horiz > self.max_radius:       # ② 水平围栏 → RTL
if alt > self.max_alt:            # ③ 高度上限 → LAND
if alt < self.min_alt and 下坠:    # ④ 高度下限 → LAND
if speed > self.max_speed:        # ⑤ 速度超限 → RTL
if tilt > self.max_tilt and alt > 1.0:   # ⑥ 倾角过大 → LAND
```

**为什么围栏用 RTL，超速用 RTL，而高度/倾角用 LAND？**

| 动作 | 语义 | 适用 |
|---|---|---|
| **RTL**（Return To Launch） | 保持飞行，自动飞回起飞点 | 位置越界、速度异常——**飞机还能飞，可以回家** |
| **LAND**（原地降落） | 就地下降 | 姿态异常、高度异常、急停——**飞机状态不安全，不能再飞远** |

**判断依据是"飞机还能不能安全飞行"**：

- 飞出去了但姿态正常 → 让它飞回来（RTL）；
- 姿态失控/翻跟头 → 别让它再飞，就地降（LAND）；
- 你按了急停 → 最保守，就地降。

这个区分很重要：**在倾角 60° 的时候让它 RTL，等于让它以危险姿态飞更远。**

### 2.3 倾角：为什么不能用速度比近似

这是我们踩过的真坑，也是本章最有价值的一段。

**早期实现**（错的）：

```python
# 反例：用水平/垂直速度比近似倾角
tilt = math.atan2(horiz_speed, vert_speed)
```

**为什么错**：悬停时垂直速度 ≈ 0，`atan2(很小的数, ≈0)` 会算出接近 **90°**。

实测日志：

```text
[WARN] 倾角过大 88° -> LAND     ← 飞机明明平稳悬停
```

于是监督层疯狂误报，把正常飞行全部打断。

**正确做法**：订阅 `vehicle_attitude`，用四元数算"机体 z 轴与世界 z 轴的夹角"：

```python
q = self.att.q                    # [w, x, y, z]
cos_tilt = 2.0 * (q[0] * q[0] + q[3] * q[3]) - 1.0
tilt = math.acos(max(-1.0, min(1.0, cos_tilt)))
```

**这个公式是怎么来的**：旋转矩阵的 (3,3) 元素等于"机体 z 轴在世界 z 轴上的投影"，也就是两者夹角的余弦。展开后正好是 `2(w² + z²) − 1`。

| 状态 | cos_tilt | tilt |
|---|---|---|
| 水平 | 1 | 0° |
| 倾斜 30° | 0.866 | 30° |
| 倾斜 45° | 0.707 | 45° |
| 翻转 180° | −1 | 180° |

**为什么必须用姿态而不是速度**：速度是**结果**，姿态是**原因**。悬停时有风也会有小速度，爬升时有垂直速度——用速度推姿态，在边界工况必然撒谎。

> 安全层的每个量都要用**权威来源**。近似公式在正常工况下看着没事，在边界工况会突然背叛你。

### 2.4 触发顺序：为什么急停放第一

检查是**短路**的：第一个满足条件就 `return`，后面的不再判。

```python
if self.estop:
    self.trigger('LAND', '外部急停')
    return
```

顺序设计的依据是**"谁最不该被延迟"**：

1. **急停**——人的意志最高优先级，必须第一个判；
2. **围栏**——位置越界最危险（可能飞出场地、撞人）；
3. **高度/速度/倾角**——状态类检查，稍慢一点可以接受。

如果顺序反了（比如倾角检查在急停之前），你在紧急情况下按急停，系统可能先被一个"倾角超限"拦住，去打 LAND 日志而不是执行你的急停意图——**虽然结果可能一样，但语义错了**。

### 2.5 阈值怎么定

阈值不是拍脑袋，要按**任务包络**推：

| 阈值 | 怎么定 | 例子 |
|---|---|---|
| `max_radius` | 任务最大水平距离 × 1.2 以上 | 正方形 3m 边 → 对角约 4.2m → 半径至少 5m |
| `max_altitude` | 任务最高高度 + 余量 | 任务 5m → 上限 8m |
| `max_speed` | 巡航速度 × 1.5 | 巡航 1.5 → 上限 8（宽松） |
| `max_tilt_deg` | 正常飞行最大倾角 + 余量 | 机动飞行约 20–30° → 上限 45° |

**课程默认值为什么这么宽松**（半径 15m、高度 25m、速度 8m/s）？因为它要兼容**所有章节**的实验。实际部署应该按当次任务收紧。

**阈值太紧的后果**：误报 → 任务被打断 → 你会想关掉它 → 等于没有安全层。
**阈值太松的后果**：真危险时没反应。

**平衡点**：宁可略松，也不要频繁误报——因为**误报会训练人忽略告警**。

### 2.6 为什么触发后不直接 disarm

一个直觉做法是"出问题就上锁（disarm）"。这在**地面上**没问题，在**空中**是灾难：上锁 = 电机停转 = 直接摔下来。

所以安全动作只有两种：**RTL**（还能飞，回家）和 **LAND**（不能飞远，就地降）。两者都保持电机运转、保持姿态控制。

**唯一的例外**是落地后的自动上锁——那是 PX4 在检测到触地后自己做的。

### 2.7 监督层自己也会失效

诚实地说，这个模块也有失效模式：

| 失效 | 表现 | 缓解 |
|---|---|---|
| 进程挂了 | 完全没保护 | 用 systemd/launch 守护、心跳监控 |
| 话题断了 | 拿不到状态，`pos is None` 直接 return | **必须报警**，不能静默 |
| 阈值配错 | 太松=没保护，太紧=误报 | 启动时打印阈值（代码已做） |
| 检查顺序错 | 急停被其它检查抢先 | 顺序写死在前 |
| 逻辑 bug | 某个条件永远不成立 | 用故障注入验证每个分支 |

注意代码里这一行：

```python
if self.pos is None or not self.pos.z_valid:
    return
```

**它什么都没做就返回了**——这是"静默失效"：监督者活着，但没有保护。**理想实现应该在这里报警或主动降落**。这是课程可以改进的点，留作思考题。

### 2.8 检查频率决定了"冲出去多远"

第 1.3 节那个细节：围栏 2.5m，实际在 3.1m 才触发。为什么？

**因为检查是周期性的**。假设检查 10Hz（每 100ms 一次）、飞行速度 1.5 m/s：

```text
每拍飞过的距离 = 1.5 m/s × 0.1 s = 0.15 m
```

所以理论上最多冲出去 0.15m。但实测冲了 0.6m——说明还有**响应延迟**：

| 延迟来源 | 量级 |
|---|---|
| 检查周期 | 100 ms |
| 命令下发到飞控生效 | 50–200 ms |
| RTL 切换、减速 | 数百 ms |

**结论**：触发距离 = 阈值 + 检查滞后 + 响应滞后。

**怎么减小**：

| 手段 | 效果 | 代价 |
|---|---|---|
| 提高检查频率 | 减小检查滞后 | CPU 占用 |
| 降速 | 减小每拍位移 | 效率 |
| **阈值留余量** | 最简单 | 保护范围变小 |

**所以阈值不能贴着实测边界设**——余量是给延迟留的。

### 2.9 与 PX4 内置 failsafe 的分工

PX4 自己有一套保护（围栏、失联、低电量）。和本章的监督层是**两层**，各管一段。

| 层 | 管什么 | 依赖 | 典型触发 |
|---|---|---|---|
| **PX4 内置** | 链路、电量、地理围栏 | 飞控自身 | 遥控失联返航 |
| **ROS2 监督层** | 任务语义、场地约束、急停 | 外部程序 + 话题 | "超出场地半径" |

**为什么两层都要**：

- 外部程序会崩、通信会断 → 需要不依赖外部的一层（PX4）；
- 飞控不知道"这次任务的场地只有 20 米" → 需要懂语义的一层（监督层）。

**配置上要避免的冲突**：如果 PX4 围栏是 100m、监督层是 5m，那实际生效的是 5m（先触发）。**层层都要收紧到合理值，而不是只设一层。**

**验证顺序**：先仿真验证监督层（本章），再配 PX4 参数（第 15 章），最后实机。

## 3. 案例：五个真实问题

### 案例 1：88° 假倾角（本章的"刺"原型）

**现象**：飞机平稳悬停，日志疯狂输出 `倾角过大 88° -> LAND`。

**原因**：用速度比近似倾角（2.3 节）。

**修复**：订阅 `vehicle_attitude`，用四元数算。

**教训**：这是"看起来能用"的代码在边界工况下崩溃的典型。**悬停时垂直速度趋近 0，除法把误差放大成 88°。**

### 案例 2：围栏太紧，正常任务被反复打断

**现象**：任务刚飞到第二个航点就 RTL，任务永远完不成。

**原因**：`max_radius=2.5` 而任务航点距原点 3m。

**诊断**：把任务航点的最大距离算出来，与阈值对比。

**修复**：阈值 ≥ 任务包络 × 1.2。**或者**改任务让它缩小——但通常是阈值错了。

### 案例 3：触发 RTL 后撞墙

**现象**：飞机越界，触发 RTL，返航路径上撞到墙。

**原因**：RTL 是**直线返航**，不避障。

**这说明什么**：安全层不解决路径规划问题。它是"保命"，不是"聪明"。如果场地有障碍，RTL 路径要预先确认可行。

**改进方向**：先用 RTL；若已知障碍，改为"原地 LAND"更安全。

### 案例 4：急停按了没反应

**现象**：`ros2 topic pub --once /safety/estop std_msgs/Bool "{data: true}"` 之后飞机没降。

**排查**：

| 检查 | 命令 |
|---|---|
| 话题有人在听吗 | `ros2 topic info /safety/estop` |
| 监督节点在跑吗 | `ros2 node list \| grep safety` |
| 状态话题有数据吗 | `ros2 topic hz /x500_0/fmu/out/vehicle_local_position` |

**最常见原因**：监督节点因为 `pos is None` 一直在 `return`（2.7 节的静默失效）。

### 案例 5：飞出去没被抓到

**现象**：飞机明显飞远了，但没有围栏事件。

**可能原因**：

1. 监督节点没启动（最常见）；
2. `max_radius` 设得太大；
3. 状态话题的命名空间不匹配（`px4_ns` 写错）；
4. 检查频率太低，飞机高速穿过边界又回来。

**逐项验证**：先确认节点活着，再看日志有没有"安全监督启动"，再 echo 状态话题。

## 4. 进阶

### 4.1 逐段读 `safety_supervisor.py`：169 行里的三个设计

**设计一：`trigger()` 的幂等保护**

```python
def trigger(self, action, reason):
    if self.action == action:
        return                        # ← 同一动作不重复发
    self.action = action
    self.dlog(f'[安全事件] {reason} -> 执行 {action}')
    ...
```

**为什么要这一行**：检查是 10Hz 的。如果越界状态持续 10 秒，没有这个判断就会发 **100 条 RTL 命令**。

**后果**：飞控被重复命令刷屏，日志被淹没，真出问题时反而看不清。

**这叫幂等（idempotent）**：同一个动作重复执行，效果与执行一次相同。**所有"持续触发的保护"都该这么写。**

**设计二：`loop()` 的两个前置门控**

```python
if self.pos is None or not self.pos.z_valid:
    return
if not self.armed():
    return
```

| 门控 | 作用 |
|---|---|
| 位置有效 | 没数据不动作（但见 2.7 的静默失效问题） |
| **已解锁** | 地面上不检查 |

**为什么"未解锁不检查"很重要**：飞机停在地面时，`horiz` 可能因为原点偏移而不为 0，`alt` 可能是负的（传感器零点）。如果不做这个门控，**地面待机就会触发降落**。

**设计三：检查顺序即优先级**

前面 2.4 节讲过：急停 → 围栏 → 高度 → 速度 → 倾角。**这个顺序写在代码里，不依赖配置**——因为它是安全语义的一部分，不该被误改。

### 4.2 监督层自己的可靠性设计

一个"保命"的模块，自己不能成为单点故障。三种加固手段：

| 手段 | 做法 | 防什么 |
|---|---|---|
| **外部看门狗** | 定时检查进程是否活着，死了就重启 | 进程崩溃 |
| **双进程互检** | 两个独立进程互相监控 | 单进程假死 |
| **飞控内置兜底** | PX4 自己的围栏/失联保护 | 外部全挂 |

**课程实现了第一种的雏形**（launch 里可以设 `respawn`），后两种留给进阶。

**一个必须接受的现实**：**没有任何软件层能保证绝对安全**。所以实机上永远需要——物理隔离、人员站位、手动接管。

### 4.3 什么该进安全层，什么不该

不是所有检查都适合放进来。判断标准：

| 该进 | 不该进 |
|---|---|
| 与任务无关的场地约束（围栏） | "飞完第 3 个航点"（任务逻辑） |
| 物理量越界（速度/倾角/高度） | "检测到人"（感知结果，可能误检） |
| 人的直接意志（急停） | "电量够不够飞完"（需要任务规划） |

**判据**：**安全层只处理"无条件必须遵守"的规则**。带条件、带推理的判断放任务层，安全层只在它们失效时兜底。

**为什么这条重要**：安全层越简单越可靠。一旦它开始"思考"，它自己就会成为 bug 来源。

## 常见误解

| 误解 | 实际情况 |
|---|---|
| "安全逻辑写进任务里就行" | 任务崩了安全就没了 |
| "出问题就 disarm" | 空中上锁等于摔机 |
| "倾角可以用速度算" | 悬停时垂直速度≈0，会算出 88° |
| "阈值越紧越安全" | 误报会让人关掉告警，反而更不安全 |
| "安全层能避障" | RTL 是直线，不避障 |
| "监督层不会失效" | 进程挂/话题断/阈值错，都会静默失效 |
| "触发后立刻降落最保险" | 姿态正常时 RTL 更安全（能飞回家） |

## 分层练习

**基础**

1. 正方形边长 3m，圆心在起飞点，算出需要的最小围栏半径。
   > 要点：对角半径 ≈ 3√2/2 ≈ 2.12m；加余量取 2.5–3m。注意若正方形从原点开角，则远端 3√2 ≈ 4.24m。

2. 为什么倾角检查要加 `and alt > 1.0` 的条件？
   > 要点：地面附近姿态本来就乱（触地、倾斜停机），避免落地时误报。

3. RTL 与 LAND 分别保持哪些控制量？
   > 要点：都保持姿态控制与电机运转；RTL 还要有位置控制飞回家。

**进阶**

4. 给监督层加一个"低电量 → RTL"检查，说明阈值怎么定。
   > 要点：按返航距离与耗电速率估，留 30% 余量。

5. 设计"连续 N 次检测到越界才触发"的防抖，讨论它会带来什么风险。
   > 要点：降低误报，但延迟响应；N 与检查频率共同决定延迟。

6. 把监督层的检查频率从 10Hz 提到 50Hz，观察触发距离的滞后变化。

**挑战**

7. 如果监督层进程崩了，怎么让系统仍然安全？给出至少两种方案。
   > 要点：外部看门狗、PX4 内置 failsafe、双进程互检。

8. 评估：PX4 自带的 failsafe（数据链丢失、低电量）与本项目监督层的职责如何划分，哪些重叠？
   > 要点：PX4 管"飞控自身与链路"，监督层管"任务语义与场地约束"。

## 小结与下一步

本章的核心是一句话：**安全层要独立、要简单、要用权威数据。**

具体你得到了三样东西：

1. **架构判断**：任务与安全分离，任务崩了安全还在；
2. **动作语义**：RTL 与 LAND 的选择依据是"还能不能安全飞"；
3. **一个反面教材**：速度比近似倾角——在正常工况下看着对，在悬停时算出 88°。

还留下一个值得继续想的问题：本文的监督层在状态话题断开时会**静默失效**。这不是 bug，而是设计缺陷——安全模块的"沉默"应该被当成"危险"，而不是"没事"。

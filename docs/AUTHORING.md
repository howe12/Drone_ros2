# 课程编写规范（AUTHORING）

> 本文件是课程内容的**编写契约**。任何新增/改写章节（包括由课程 agent 生成的内容）都必须遵守。
> 方法论来源：本地 skill `course-writer`（六段式）、`course-task-design`（任务卡）、
> `course-beginner-audit`（小白审计）、`human-writing`（活人感写作）。

## 一、章节结构：六段检查清单，不是填空模板

下面六段是**自检清单**，用于检查章节是否讲完整；允许按章节类型合并、调整顺序或省略（例如概念章可没有实验，实验章可弱化回顾）。不要为了凑齐段落写空话。

| 段 | 建议标记 | 要求 | 常见错误 |
|---|---|---|---|
| 1 本章问题 | `## 本章问题` | 用具体工程场景说明要解决什么；陈述句即可，可含问题但不强制设问 | 空泛提问、为提问而提问 |
| 2 前置与回顾 | `## 前置与回顾` | 说明读者已具备的能力、本章依赖的上一章产出（第一章写"从零开始"） | 写成"第 N 章讲 X"式预告 |
| 3 学习目标 | `## 学习目标` | 表格：维度 / 学习前 / 学习后，5 个维度左右 | 写成 bullet 列表 |
| 4 主体内容 | `## 主体内容` | 按依赖关系分节；每节讲清机制、代码位置和参数；需要时给 ❌/✅ 对比，但不必每节都有 | 知识点罗列、每节都硬凑对比 |
| 5 实验实战 | `## 实验实战` | 观察 → 验证 → 分析；每步给目标、命令、**预期输出/判分结果** | 只给一条命令、无预期输出 |
| 6 小结与下一步 | `## 小结` 或 `## 下一步` | 有真实知识依赖才衔接后续章节；可只做小结，不制造悬念 | "下一章将介绍…"式预告、强行埋钩子 |

章尾按需附加：**任务卡**（见二）+ **检查清单**（"我能…"能力自检，6–8 项）。

## 二、任务卡固定六段（每个练习都是完整卡，不允许零散点子）

```markdown
### 任务卡 N：<一句话功能>

| 段 | 内容 |
|---|---|
| 1 要实现的功能 | 有看得见的结果（飞机飞到哪、日志出现什么） |
| 2 通信骨架/前置 | 谁发谁收、话题、消息类型；零前置时写明学生已会什么 |
| 3 参考 prompt | 学生可整段复制去问 AI 的完整提问（角色 + 目标 + 约束 + 先给代码别讲理论） |
| 4 执行步骤 | 可跑命令 + **预期输出**（逐条） |
| 5 验收标准 | 可核验的勾选项/填空，不说"看起来正常" |
| 6 原理 + 扩学 | 这张卡在教哪条原理，扩学到哪个场景 |
```

**每张卡埋一个刺**：故意制造一个故障让学生亲手修好（消息类型不匹配、频道名串、频率不够、客户端先于服务端启动、QoS 不匹配）。
踩一次比讲十次管用。卡尾落到"讲给人听"：把链路/代码讲给零基础同学，对方能复现才算过。

## 三、小白视角三维修审计（每章发布前自检）

| 维度 | 检查项 |
|---|---|
| 路径 | 命令里的路径学生机器上存在吗？有没有"第 0 步"创建/进入工作目录？相对路径是否正确？ |
| 命令 | 能直接复制粘贴就跑吗？环境 source 方式前后一致吗？本地/云端命令有没有混？ |
| 预期 | 有没有终端输出样例？有没有说"运行后你应该看到…"？截图/日志有吗？ |

优先级：**P0 缺第0步/环境不一致** → **P1 片段代码/缺衔接** → **P2 门槛无降级提示** → **P3 编号不一致**。

## 四、文风规范（工程教材：清楚、克制、有证据）

> 参考阅读：[hello-agents 第一章](https://datawhalechina.github.io/hello-agents/#/chapter1/)。
> 借鉴它的读者路径、层层展开、理论后接实作、图文与代码并用；不复制句式密度。
> 我们写的是无人机工程课，技术事实和可复现实验是主线，问题、类比和故事只在确实有助理解时使用。

### 4.1 章节脉络：沿着真实工程问题展开

一节内容通常按以下顺序组织，不要求机械保留所有小标题：

1. **现象或任务**：学生会看到什么、要完成什么；优先使用仓库里的实测现象。
2. **必要概念**：只解释完成当前任务需要的原理和术语。
3. **数据链路或代码位置**：明确输入、处理、输出，以及对应话题、函数或参数。
4. **操作和证据**：给可复制的命令，说明关键输出、截图或指标应是什么。
5. **边界与故障**：展示常见错误及诊断方法；未验证内容必须明确标注。
6. **下一步**：确有知识依赖时再衔接，不为过渡硬造悬念。

概念顺序按依赖关系递进。可以用问题引出章节，但不规定每几段必须提问；可以用类比，但必须能准确解释机制，不能只是增加修辞。

### 4.2 理论与实践：围绕同一个学习目标往返

整体建议理论与实践约 45:55，按章节类型调整，不为达到比例硬塞内容。推荐节奏：
**观察现象 → 提出解释 → 查代码/接口 → 动手验证 → 分析结果**。理论不脱离本章实验，实验也不退化为复制命令。

### 4.3 语言与修辞：自然，不表演

- 用清楚、准确的中文。可用“我们”和“你”，但不刻意营造对话感。
- **设问是可选工具**：只有确实能帮助定位困惑时才用；避免连续反问、问后自答的固定套路。
- **类比是可选工具**：只有能准确映射关键机制时才用；不规定“一个概念一个类比”。优先使用真实工程例子、数据流和失败现象。
- 避免模板化转折、口号和空词；不要反复写“核心、赋能、范式”。
- 术语首次出现写中文名、英文名/缩写（如需要）和准确的一句定义；后文统一用一个名称。
- 句子长短服从信息复杂度；操作步骤用短句，因果解释一段只讲一个主要关系。
- 图表必须承担信息：标注来源、坐标系、单位和关键结论。装饰图、重复截图不算有效插图。

### 4.4 工程内容的写法

- 命令注明**在哪个目录、哪个终端、是否需要先 source**，给出复制后可执行的版本。
- 代码讲解说明改哪段、输入输出、关键参数、预期日志/话题/状态；不能只贴代码。
- 数值写清单位、坐标系和测量来源。比如“高度 5m”须说明是 Gazebo 世界系真值还是 PX4 局部估计。
- 结果区分**实测通过 / 部分通过 / 未验证**，不得把预期结果写成实测。
- 出错处理按“现象 → 可能原因 → 验证命令 → 修复”写，避免只给结论。

### 4.5 改写样例：用时序和证据解释 Offboard

> PX4 切入 Offboard 前，要求外部控制器已经持续发送 `OffboardControlMode` 和有效设定点。课程节点以 10Hz 发布这两类消息；满足预流条件后，才发送切换模式与解锁命令。若先发模式命令、后开始发设定点，PX4 会拒绝切换或触发 Offboard loss failsafe。
>
> 顺序是：**预流 → 请求 Offboard → 解锁**。验证时观察 `/x500_0/fmu/out/vehicle_status`：`nav_state` 应进入 Offboard，`arming_state` 从 1 变为 2。若状态未变化，再检查话题是否匹配、QoS 是否兼容、EKF 是否稳定。

这段按“机制 → 本项目实现 → 错误后果 → 可观察证据”展开。类比可以作为辅助，但不能替代消息时序和状态验证。

## 五、写作底线：事实准确、表达克制

- 先材料后文字：每个结论必须有**实测数据/日志/截图**托底；没有就写“待验证”。
- 不用机构腔、营销腔和空洞排比；避免重复解释同一个结论。
- 版本、命令、参数、分支名写前核对仓库现状，不凭记忆。

## 五、事实来源铁律（course-writer 源码头审计）

1. 代码行为以**仓库源码**为准，不以 README 描述为准
2. 命令以 `catalog/scenarios.yaml` 的 `command` 字段为准，**不要自己编**
3. 判分阈值以 `catalog/scenarios.yaml` 的 `metrics` 为准，不写"大约/应该"
4. 未验证的实验（`status: unverified`）只能写研究挑战，**不得作为作业**

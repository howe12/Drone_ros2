# 课程编写规范（AUTHORING）

> 本文件是课程内容的**编写契约**。任何新增/改写章节（包括由课程 agent 生成的内容）都必须遵守。
> 方法论来源：本地 skill `course-writer`（六段式）、`course-task-design`（任务卡）、
> `course-beginner-audit`（小白审计）、`human-writing`（活人感写作）。

## 一、章节结构：六段检查清单，不是填空模板

下面六段是**自检清单**，用于检查章节是否讲完整；允许按章节类型合并、调整顺序或省略（例如概念章可没有实验，实验章可弱化回顾）。不要为了凑齐段落写空话。

| 段 | 建议标记 | 要求 | 常见错误 |
|---|---|---|---|
| 1 本章问题 | `## 本章问题` | 用具体工程场景说明要解决什么；陈述句即可，可含问题但不强制设问 | 空泛提问、为提问而提问 |
| 2 前置与回顾 | `## 前置与回顾` | 说明读者已具备的能力、本章依赖的上一章产出（第一章写"从零开始"） | 写成"第 N 章讲 X"式预告 |
| 3 学习目标 | `## 学习目标` | 表格：维度 / 学习前 / 学习后，5 个维度左右 | 写成 bullet 列表 |
| 4 主体内容 | `## 主体内容` | 按依赖关系分节；每节讲清机制、代码位置和参数；需要时给 ❌/✅ 对比，但不必每节都有 | 知识点罗列、每节都硬凑对比 |
| 5 实验实战 | `## 实验实战` | 观察 → 验证 → 分析；每步给目标、命令、**预期输出/判分结果** | 只给一条命令、无预期输出 |
| 6 小结与下一步 | `## 小结` 或 `## 下一步` | 有真实知识依赖才衔接后续章节；可只做小结，不制造悬念 | "下一章将介绍…"式预告、强行埋钩子 |

章尾按需附加：**任务卡**（见二）+ **检查清单**（"我能…"能力自检，6–8 项）。

## 二、任务卡固定六段（每个练习都是完整卡，不允许零散点子）

```markdown
### 任务卡 N：<一句话功能>

| 段 | 内容 |
|---|---|
| 1 要实现的功能 | 有看得见的结果（飞机飞到哪、日志出现什么） |
| 2 通信骨架/前置 | 谁发谁收、话题、消息类型；零前置时写明学生已会什么 |
| 3 参考 prompt | 学生可整段复制去问 AI 的完整提问（角色 + 目标 + 约束 + 先给代码别讲理论） |
| 4 执行步骤 | 可跑命令 + **预期输出**（逐条） |
| 5 验收标准 | 可核验的勾选项/填空，不说"看起来正常" |
| 6 原理 + 扩学 | 这张卡在教哪条原理，扩学到哪个场景 |
```

**每张卡埋一个刺**：故意制造一个故障让学生亲手修好（消息类型不匹配、频道名串、频率不够、客户端先于服务端启动、QoS 不匹配）。
踩一次比讲十次管用。卡尾落到"讲给人听"：把链路/代码讲给零基础同学，对方能复现才算过。

## 二·五、零基础读者规则（章节内容不得默认读者已懂）

读者假设：**会 Linux 命令行与 Python 基础，没有 ROS2/PX4 经验**。章节正文不得出现未解释的前置概念。

必须遵守：

1. **首次出现即解释**：生僻词（Offboard、EKF、NED、QoS、命名空间、里程计、栅格地图、TF…）第一次出现时，用一句话说明它是什么、在本项目中对应哪个实体或话题，再继续叙述。
2. **命令要讲清上下文**：每条命令说明在哪个目录、哪个终端、是否需要先 `source`；涉及命名空间时说明它来自哪里（例如 `gz_x500_mono_cam` 推导出 `/x500_mono_cam_0`）。
3. **概念给出可观察对象**：抽象机制要对应到能看到的证据（话题名、日志行、状态码、判分指标）。例如解释 Offboard 时，要说明看 `vehicle_status` 的 `nav_state`。
4. **坐标与单位必须显式**：出现位置、速度、高度时，写明坐标系（NED / ENU / 机体系 / 像素系）和单位。
5. **故障要能定位**：排障段落写"现象 → 可能原因 → 验证命令 → 修复"，不只给结论。
6. **章节篇幅服从内容**：为讲清原理可以加长；禁止为了简短省略必要背景，也禁止为凑篇幅重复解释。

章节开头可用一小段"本章涉及的新概念"列表（术语 + 一句话解释 + 后续详述位置），帮助零基础读者先建立词汇表。

**概念说明的三条硬规则**：

1. 每个概念**要么就地解释，要么链接[术语表](GLOSSARY.md)**，不允许裸用（如直接写"姿态控制、EKF、模式管理"而不解释）。
2. 新引入的术语必须**同步登记到 GLOSSARY.md**（白话解释 + 深入章节）。
3. 背景知识（机型分类、飞行原理、飞控职责、命名由来、软件生态）统一放[第 00 章](course/00-basics.md)，正文链接过去，不重复展开。

## 二·六、配图占位规范（生图提示词预留）

需要原理图、架构图、流程图但暂无图片时，**必须**在正文中插入占位块，并写好生图提示词，便于后续用生图模型补齐。占位块格式：

```markdown

```

规则：

- `id` 全局唯一，命名 `fig-ch<章号>-<主题>`；图片文件先放 `images/PLACEHOLDER-<id>.png`（暂无真实图片时可先用同名占位说明，不影响结构检查）。
- `caption` 写清这张图说明什么；`alt` 给无障碍与检索用；`prompt` 是给生图模型的完整提示词，**中文、具体、含标注要求**。
- 提示词统一要求：技术教材插图、白底或浅色底、扁平化、中文标注、不出现真人/卡通/水印；架构图要标出组件名与消息方向，流程图要标出判断条件。
- 一张图只承担一个说明任务；不要为装饰插图。
- 已有真实截图（Gazebo 画面、RViz、终端输出）的地方直接引用 `images/`，不再重复占位。

## 二·七、运行截图占位规范（待实际运行时补图）

与"生图占位"（二·六，画架构/原理图）不同，**运行截图**来自实际跑仿真时的真实画面：Gazebo 窗口、终端输出、判分报告、RViz 等。未截图时用下面格式占位，并写清"何时截、截什么、用什么命令"。

```markdown
<!-- SCREENSHOT_PLACEHOLDER

![图 1.3 首飞画面](images/PLACEHOLDER-shot-ch01-first-flight.png)
```

规则：

- `id` 命名 `shot-ch<章号>-<主题>`，图片先放 `images/PLACEHOLDER-<id>.png`。
- `when` 说明运行时机（哪条命令之后、日志出现什么时）；`what` 说明画面里必须能看到什么；`how` 给可复制的截图命令（便于后续批量补图）。
- 已有真实截图的（如 `images/04_xtd2_x500_takeoff.png`）直接引用，**不重复占位**。
- 截图必须能支撑正文结论：例如讲"起飞到 5m"，截图就要能看出飞机离地高度。

## 二·八、AI 融入规范（内嵌在任务与问题中，不设独立环节）

AI 是贯穿全课程的**默认工具**：提出问题和实验要求时，顺势提示"可用 AI 辅助理解或生成"。**不要**在章节里专设"AI 实验室/AI 环节"小节——那会把 AI 变成额外负担，而不是学习工具。

### 怎么融入

| 位置 | 做法 |
|---|---|
| 任务卡第 3 段 | 写"AI 提示"：学生可复制的提问（含课程上下文），而不是只给命令 |
| 任务卡第 4 段 | 执行步骤里提示"可让 AI 解释某步，但用这些命令验证" |
| 练习/思考题 | 加一句"可让 AI 帮你理解或生成初稿，但需逐行看懂并跑通" |
| 检查清单 | 含一条"我能解释 AI 给我的代码/答案" |
| 全书 | `docs/AI_GUIDE.md` 作为随时可查的方法页（上下文模板、易错对照），不强制每章跳转 |

### 硬性要求

1. **先自己想，再问 AI**：问题先让学生形成判断，AI 用于补充和纠偏。
2. **给足上下文**：AI 提示必须包含版本、命名空间、接口名、QoS——否则 AI 按通用 PX4/ROS2 回答，与锁版本环境不符。
3. **必须验证**：提示学生用命令核对 AI 答案（本课程典型坑：`OffboardControlMode` 字段是 `thrust_and_torque`/`direct_actuator` 而非旧版 `actuator`；QoS 必须 BEST_EFFORT；命名空间与 `target_system` 匹配）。
4. **不代写**：AI 给思路和片段，学生自己整合、跑通、能解释。
5. **重点在理解与实操**：AI 提示服务于"搞懂原理、做出结果"，不是单独的 AI 练习。

## 二·九、表达四规则（借鉴 colah.github.io）

参照 <https://colah.github.io/>（尤其 [Understanding LSTM Networks](https://colah.github.io/posts/2015-08-Understanding-LSTMs/)）。它最值得学的不是文采，而是**四件可执行的事**：

### 1. 开篇是场景，不是摘要

❌ "本章将介绍 PX4 的控制模式与接口规范。"
✅ "你敲下第三条命令。几秒后弹出一个窗口——一架橙色的四旋翼停在地上，一动不动。"

用具体的人、动作、疑问开场；把"本章要解决什么"放在场景之后，用编号列清。

### 2. 图注是**可见的加粗陈述句**

- 位置：图片下方**单独一行**加粗，不能只写在 `IMAGE_PLACEHOLDER` 的 `caption` 元数据里（注释不渲染，读者看不到）。
- 句式：一句能独立成立的结论，不是"图 3：系统架构图"这种标签。

```markdown
![图 1.3 数据链路](images/xxx.png)

**图 1.3　指令往下走，状态往上走；中间那一段断了，全线哑巴。**
```

### 3. 贯穿锚点：全章回扣同一个具体对象

选定一个贯穿物（一次首飞的日志、一个场景的数据、一段代码），每个原理小节都回到它："日志第 2 行那句话，翻译过来就是……"。读者不必每节重新建模。

### 4. 两个降压结构

- **"先跑再懂"提示**：开头明确写"第一遍看不懂正常，第 N 章会展开"，降低中途放弃率。
- **"你可能卡在这里"表**：`现象 | 最可能原因 | 先跑这条命令`，5 行以内。让读者卡住时能自救，而不是掉出课程。

### 结构可预期

每节固定走：**现象 → 解释 → 证据**。读者始终知道自己在哪一步。章首可加"本章地图"小表（步骤 / 做什么 / 拿到什么证据）。

## 三、小白视角三维修审计（每章发布前自检）

| 维度 | 检查项 |
|---|---|
| 路径 | 命令里的路径学生机器上存在吗？有没有"第 0 步"创建/进入工作目录？相对路径是否正确？ |
| 命令 | 能直接复制粘贴就跑吗？环境 source 方式前后一致吗？本地/云端命令有没有混？ |
| 预期 | 有没有终端输出样例？有没有说"运行后你应该看到…"？截图/日志有吗？ |

优先级：**P0 缺第0步/环境不一致** → **P1 片段代码/缺衔接** → **P2 门槛无降级提示** → **P3 编号不一致**。

## 四、文风规范（工程教材：清楚、克制、有证据）

> 参考阅读：[hello-agents 第一章](https://datawhalechina.github.io/hello-agents/#/chapter1/)。
> 借鉴它的读者路径、层层展开、理论后接实作、图文与代码并用；不复制句式密度。
> 我们写的是无人机工程课，技术事实和可复现实验是主线，问题、类比和故事只在确实有助理解时使用。

### 4.1 章节脉络：沿着真实工程问题展开

一节内容通常按以下顺序组织，不要求机械保留所有小标题：

1. **现象或任务**：学生会看到什么、要完成什么；优先使用仓库里的实测现象。
2. **必要概念**：只解释完成当前任务需要的原理和术语。
3. **数据链路或代码位置**：明确输入、处理、输出，以及对应话题、函数或参数。
4. **操作和证据**：给可复制的命令，说明关键输出、截图或指标应是什么。
5. **边界与故障**：展示常见错误及诊断方法；未验证内容必须明确标注。
6. **下一步**：确有知识依赖时再衔接，不为过渡硬造悬念。

概念顺序按依赖关系递进。可以用问题引出章节，但不规定每几段必须提问；可以用类比，但必须能准确解释机制，不能只是增加修辞。

### 4.2 理论与实践：围绕同一个学习目标往返

整体建议理论与实践约 45:55，按章节类型调整，不为达到比例硬塞内容。推荐节奏：
**观察现象 → 提出解释 → 查代码/接口 → 动手验证 → 分析结果**。理论不脱离本章实验，实验也不退化为复制命令。

### 4.3 语言与修辞：自然，不表演

- 用清楚、准确的中文。可用“我们”和“你”，但不刻意营造对话感。
- **设问是可选工具**：只有确实能帮助定位困惑时才用；避免连续反问、问后自答的固定套路。
- **类比是可选工具**：只有能准确映射关键机制时才用；不规定“一个概念一个类比”。优先使用真实工程例子、数据流和失败现象。
- 避免模板化转折、口号和空词；不要反复写“核心、赋能、范式”。
- 术语首次出现写中文名、英文名/缩写（如需要）和准确的一句定义；后文统一用一个名称。
- 句子长短服从信息复杂度；操作步骤用短句，因果解释一段只讲一个主要关系。
- 图表必须承担信息：标注来源、坐标系、单位和关键结论。装饰图、重复截图不算有效插图。

### 4.4 工程内容的写法

- 命令注明**在哪个目录、哪个终端、是否需要先 source**，给出复制后可执行的版本。
- 代码讲解说明改哪段、输入输出、关键参数、预期日志/话题/状态；不能只贴代码。
- 数值写清单位、坐标系和测量来源。比如“高度 5m”须说明是 Gazebo 世界系真值还是 PX4 局部估计。
- 结果区分**实测通过 / 部分通过 / 未验证**，不得把预期结果写成实测。
- 出错处理按“现象 → 可能原因 → 验证命令 → 修复”写，避免只给结论。

### 4.5 改写样例：用时序和证据解释 Offboard

> PX4 切入 Offboard 前，要求外部控制器已经持续发送 `OffboardControlMode` 和有效设定点。课程节点以 10Hz 发布这两类消息；满足预流条件后，才发送切换模式与解锁命令。若先发模式命令、后开始发设定点，PX4 会拒绝切换或触发 Offboard loss failsafe。
>
> 顺序是：**预流 → 请求 Offboard → 解锁**。验证时观察 `/x500_0/fmu/out/vehicle_status`：`nav_state` 应进入 Offboard，`arming_state` 从 1 变为 2。若状态未变化，再检查话题是否匹配、QoS 是否兼容、EKF 是否稳定。

这段按“机制 → 本项目实现 → 错误后果 → 可观察证据”展开。类比可以作为辅助，但不能替代消息时序和状态验证。

## 五、写作底线：事实准确、表达克制

- 先材料后文字：每个结论必须有**实测数据/日志/截图**托底；没有就写“待验证”。
- 不用机构腔、营销腔和空洞排比；避免重复解释同一个结论。
- 版本、命令、参数、分支名写前核对仓库现状，不凭记忆。

## 六、事实来源铁律（course-writer 源码头审计）

1. 代码行为以**仓库源码**为准，不以 README 描述为准
2. 命令以 `catalog/scenarios.yaml` 的 `command` 字段为准，**不要自己编**
3. 判分阈值以 `catalog/scenarios.yaml` 的 `metrics` 为准，不写"大约/应该"
4. 未验证的实验（`status: unverified`）只能写研究挑战，**不得作为作业**

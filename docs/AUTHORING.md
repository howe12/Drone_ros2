# 课程编写规范（AUTHORING）

> 本文件是课程内容的**编写契约**。任何新增/改写章节（包括由课程 agent 生成的内容）都必须遵守。
> 方法论来源：本地 skill `course-writer`（六段式）、`course-task-design`（任务卡）、
> `course-beginner-audit`（小白审计）、`human-writing`（活人感写作）。

## 一、章节固定六段式（缺一段 = 不合格）

| 段 | 标记 | 要求 | 常见错误 |
|---|---|---|---|
| 1 驱动问题 | `## ❓ 驱动问题` | 具体场景制造认知缺口 → 抛一个尖锐问题 → 一句宣言式结论 | 直接罗列知识点、问题太虚 |
| 2 上一章回顾 | `## 📚 上一章回顾` | 关联上一章的**具体产出**，说明为什么需要本章（第一章写"从零开始"） | 写"第 N 章讲 X"式预告 |
| 3 学习目标 | `## 🎯 学习目标` | **三列表格**：维度 / ❌ 学习前 / ✅ 学习后，至少 5 个维度 | 写成 bullet 列表 |
| 4 主体内容 | `## 📖 主体内容` | 多小节，每节一个原理点；每节至少一张 ❌/✅ 对比；关键结论用引用块高亮 | 只讲正确做法不给反例 |
| 5 实验实战 | `## 🔬 实验实战` | 六阶段渐进：观察 → 探索 → 交互 → 导出 → 阅读 → 反思；每阶段：目标 + 命令 + **预期输出** | 只给一条命令、没有预期输出 |
| 6 新问题 | `## ❓ 新问题` | 抛一个必须在下一章回答的问题（制造需求，不是预告） | 写"下一章将介绍…" |

章尾固定附加：**任务卡**（见二）+ **检查清单**（"我能…"能力自检，6–8 项）。

## 二、任务卡固定六段（每个练习都是完整卡，不允许零散点子）

```markdown
### 任务卡 N：<一句话功能>

| 段 | 内容 |
|---|---|
| 1 要实现的功能 | 有看得见的结果（飞机飞到哪、日志出现什么） |
| 2 通信骨架/前置 | 谁发谁收、话题、消息类型；零前置时写明学生已会什么 |
| 3 参考 prompt | 学生可整段复制去问 AI 的完整提问（角色 + 目标 + 约束 + 先给代码别讲理论） |
| 4 执行步骤 | 可跑命令 + **预期输出**（逐条） |
| 5 验收标准 | 可核验的勾选项/填空，不说"看起来正常" |
| 6 原理 + 扩学 | 这张卡在教哪条原理，扩学到哪个场景 |
```

**每张卡埋一个刺**：故意制造一个故障让学生亲手修好（消息类型不匹配、频道名串、频率不够、客户端先于服务端启动、QoS 不匹配）。
踩一次比讲十次管用。卡尾落到"讲给人听"：把链路/代码讲给零基础同学，对方能复现才算过。

## 三、小白视角三维修审计（每章发布前自检）

| 维度 | 检查项 |
|---|---|
| 路径 | 命令里的路径学生机器上存在吗？有没有"第 0 步"创建/进入工作目录？相对路径是否正确？ |
| 命令 | 能直接复制粘贴就跑吗？环境 source 方式前后一致吗？本地/云端命令有没有混？ |
| 预期 | 有没有终端输出样例？有没有说"运行后你应该看到…"？截图/日志有吗？ |

优先级：**P0 缺第0步/环境不一致** → **P1 片段代码/缺衔接** → **P2 门槛无降级提示** → **P3 编号不一致**。

## 四、文风规范（参照 hello-agents 第 1 章逐段分析）

> 参照对象：<https://datawhalechina.github.io/hello-agents/#/chapter1/>
> 结论：**脉络与语义照搬，配比与体例按实操课反转**。

### 4.1 可照搬的五条（他们做得最好的地方）

1. **问题链驱动，而不是知识点罗列**
   每个新概念都从上一种方法的局限里推出来。原文写智能体演进：反射式 → 局限性提问 → 基于模型 → 再提问 → 基于目标 → 再提问 → 基于效用 → 再提问 → 学习型。
   平均每 2–3 段出现一个设问句，且问句后必须紧跟回答，绝不悬空。
   → 我们的用法：每章先列 3–5 个问题构成链条，正文逐个回答。例（第 2 章）：
   为什么它听话 → 心跳是什么 → 为什么是"设定点"而不是"位置" → 为什么 z 是负的 → 为什么 EKF 会骗人。

2. **一个抽象概念配一个生活类比**（原文一章 12+ 个：恒温器、隧道里的车、棋手、图书管理员、牙牙学语的孩童、安全气囊、高频交易）
   → 我们的灰机类比清单：PX4 = 小脑/脊髓，Gazebo = 场地与感官，EKF = 内耳前庭，Offboard = 把遥控器交给程序，
   QoS = 对讲机频道与加密方式，EKF 原点重置 = 蒙眼后被搬走还坚持说自己在原地，判分 = 考试而不是自评。

3. **术语三段式**：中文名（English，缩写）→ 加粗 → 一句白话解释；首次给全称，后文用缩写。

4. **实战节五步体例**：目标 → 任务定义 → 准备（装什么）→ 分步可运行片段（每步一段完整代码）→ **贴真实输出并解读**。
   → 对应我们的"六阶段实验"：每阶段 = 目标一句话 + 命令 + 预期输出 + 一句解读。

5. **章末三件套**：问答式小结（回到章首的问题逐个回答）→ 承上启下的一问 → 习题（明确"没有标准答案，重批判性思维"）。

### 4.2 必须反转的三处（因为我们是实操课，不是概念课）

| 维度 | hello-agents | 我们 |
|---|---|---|
| 理论/实操配比 | 约 70 / 30 | **约 45 / 55**，每节理论不超过 2 屏，紧接一个可跑动作 |
| 图示体例 | 论文式示意图（png） | **实拍截图 + 真值曲线**（Gazebo 画面、RViz、误差表），表格用 markdown |
| 篇幅 | 单章 5000 字+ | **1500–2500 字**，以命令/代码/指标为主，禁止概念堆叠 |

### 4.3 句子级规则

- 人称：主体用"我们"，读者用"你"；不用"笔者""本文"。
- 设问：每 2–3 段一个问句，问完立刻答；一个问句不得连跨两节。
- 段落：3–6 句；概念密集处一句一段。
- 衔接：每节末一句转折（"如果…又该怎么办？"），每章末一句悬念（只给问题，不给答案）。
- 加粗只给**术语**与**结论句**，不整段加粗。
- 术语首次出现中英对照；中文全角标点。
- 禁用：机构腔（"本文旨在""综上所述"）、营销腔、空洞排比、未经实测的"预期效果"。

### 4.4 改写样例（第 2 章 2.1 节前后对比）

❌ 现版（知识罗列）：

> PX4 允许外部计算机（ROS2 节点）直接控制飞机，但有三条硬规则：
> 1. 心跳流必须以 >2Hz 持续发布；2. 设定点流切入前就要预流；3. 模式与解锁命令。

✅ 目标风格（问题链 + 类比）：

> 想象你把手里的遥控器交给一个程序。它会飞吗？
>
> 在 PX4 的世界里，这个"交出控制权"的动作有个正式名字，叫 Offboard 模式。但 PX4 并不轻信任何人——
> 在你真正接管之前，它要求你先证明三件事。
>
> 第一件是心跳。就像对讲机必须在通话时持续按着发射键，你的节点也必须以每秒十次的频率
> 喊一声"我在"。停超过半秒，飞控立刻判定你掉线，把控制权收回。
>
> 那如果只喊"我在"、不告诉它往哪飞呢？也不行。这就是第二件事，设定点……
>
> （后续同构：每个要素 = 一个设问 + 一个类比 + 一条硬规则 + 一组 ❌/✅）

## 五、写作风格底线（活人感 + 技术准确）

- 先材料后文字：每个结论必须有**实测数据/日志/截图**托底；没有就写"待验证"，**禁止编造**
- 不用机构腔、不用营销腔；用"我们"视角 + 具体场景
- 叙事段落避免"不是…而是…"翻案句式；技术表格/代码不受此限
- 版本类事实（工具版本、分支名、commit）写前核对仓库现状，不凭记忆

## 五、事实来源铁律（course-writer 源码头审计）

1. 代码行为以**仓库源码**为准，不以 README 描述为准
2. 命令以 `catalog/scenarios.yaml` 的 `command` 字段为准，**不要自己编**
3. 判分阈值以 `catalog/scenarios.yaml` 的 `metrics` 为准，不写"大约/应该"
4. 未验证的实验（`status: unverified`）只能写研究挑战，**不得作为作业**
